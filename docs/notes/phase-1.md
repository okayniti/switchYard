# Phase 1: cluster and store, in plain English

What Phase 1 built: a local Kubernetes cluster running a real WooCommerce store, reachable at **http://shop.localtest.me**, configured automatically and safe to re-deploy. This note explains every Kubernetes object involved and why it exists, so each one can be defended in an interview.

## The cluster (k3d)

**k3d** runs **k3s** (a small, certified Kubernetes distribution) inside Docker containers. `scripts/k3d-up.sh` creates one server node, pinned to `rancher/k3s:v1.35.5-k3s1`.

k3s ships three things this project relies on:

| Built-in | What it does for us |
|----------|---------------------|
| **Traefik** | the Ingress controller: reads Ingress objects and routes HTTP by hostname |
| **local-path provisioner** | turns a PersistentVolumeClaim into a directory on the node |
| **NetworkPolicy controller** | enforces NetworkPolicies (used from Phase 2) |

A VPS running k3s has exactly the same three, so local and prod differ only in Helm values (hostnames, TLS, image tags, secrets). That's the parity argument.

**How a browser reaches the store:**

1. `shop.localtest.me` is public DNS that always resolves to 127.0.0.1. (Fallback: add it to the hosts file.)
2. k3d maps host port 80/443 to its load-balancer container.
3. The load balancer forwards to Traefik.
4. Traefik matches the `Host` header against Ingress rules and forwards to the `wordpress` Service.

**Windows gotcha:** the API server is bound to `127.0.0.1:6550` (`--api-port`), because the default kubeconfig address (`host.docker.internal`) resolved to an unreachable WSL IP.

**Windows gotcha after a Docker restart:** the k3d load balancer can keep the server's *old* container IP, so kubectl gets `EOF`. Fix it with `docker restart k3d-switchyard-serverlb`. No data is touched.

## Namespaces: three trust zones

The umbrella chart creates them itself:

| Namespace | Contains | Exposure |
|-----------|----------|----------|
| `store` | WordPress, MariaDB, setup Job | storefront is public via Ingress |
| `mcp` | upstream MCP servers (Phase 2+) | never public |
| `platform` | gateway, dashboard, Postgres (Phase 3+) | dashboard and `/mcp` public |

The namespaces are the boundaries NetworkPolicies are written against. The Helm release record itself lives in `default`.

## Objects in the `store` namespace

### Secret `mariadb`
Holds the DB root and app passwords, as random 32-character strings.

- **Generated by Helm on the first install.** On every later install, the template calls `lookup` to read the existing Secret and reuse its values, so passwords never rotate. If they rotated, the DB on disk would reject the new ones.
- `helm.sh/resource-policy: keep` means the Secret survives a `helm uninstall`, so the data on the volume stays readable.
- **In prod**, `existingSecret` points at a Secret created out-of-band and Helm generates nothing.

### StatefulSet `mariadb` + PVC `data-mariadb-0`

- **Why a StatefulSet, not a Deployment:** it gives the pod a stable identity (`mariadb-0`), and its `volumeClaimTemplates` create a PVC that is bound to that identity and kept even if the pod is deleted. Databases need exactly that.
- **Image:** `mariadb:11.8.9` (the current LTS line), running as the image's `mysql` user (uid 999). It's not root.
- **Read-only root filesystem:** the only writable paths are the data volume, `/run/mysqld` (the socket) and `/tmp`. The last two are `emptyDir` volumes, which are scratch space that lives as long as the pod.
- **Probes,** all using `healthcheck.sh --connect --innodb_initialized`, which ships with the image:
  - **startup:** allows up to 5 min for first-boot initialization before the other probes start
  - **readiness:** the pod only receives traffic once InnoDB is up
  - **liveness:** restarts a wedged server
- **Resources:** requests 100m CPU / 256Mi; limits 1 CPU / 512Mi.
  - *Requests* are what the scheduler reserves.
  - *Limits* are the ceiling: going over the memory limit gets the container OOM-killed.

### Service `mariadb` (headless)
`clusterIP: None` means DNS returns the pod IP directly (`mariadb.store.svc.cluster.local`). That's the standard way to address a StatefulSet. It has no external exposure.

### PVC `wordpress-content`
2Gi, ReadWriteOnce, local-path. It holds WordPress core and `wp-content` (plugins, uploads), and is also kept on uninstall.

**local-path gotcha:** volumes are root-owned `0777` host directories, and `fsGroup` doesn't apply to them. The non-root container can write into the volume root but can't `chmod` it, and the image's first-boot copy needs that. The fix:
- an **init container** running as uid 33 creates `html/`, which www-data then owns;
- WordPress mounts that **subPath** at `/var/www/html`.

### Deployment `wordpress`

- **Image:** our `switchyard-wordpress:dev`, built from the official `wordpress:7.1.3-php8.3-apache` (pinned by digest) plus:
  - wp-cli 2.12.0, checked against its SHA-512
  - WooCommerce 11.2.1 zip, checked against its SHA-256
- **Non-root:** Apache runs as **www-data (uid 33) on port 8080**. Unprivileged users can't bind port 80, so the Service maps 80 → 8080.
- **`strategy: Recreate`:** the volume is ReadWriteOnce, so the old pod must stop before the new one starts. A rolling update would deadlock on the volume.
- **Env:** DB host, name and user, plus the password from the `mariadb` Secret via `secretKeyRef`, so the password is never written into the manifest. `WORDPRESS_CONFIG_EXTRA` pins `WP_HOME`/`WP_SITEURL` to the public URL, so WordPress never redirects to an internal name.
- **Outbound HTTP is blocked** (`WP_HTTP_BLOCK_EXTERNAL`, auto-updates off, file editor off). The store needs no internet, and remote calls stalling on a flaky network were the likely cause of one hung upgrade.
- **Probes:**
  - **readiness:** `GET /wp-login.php`. This exercises PHP and the DB, so a broken store drops out of the Service and Traefik stops sending traffic to it.
  - **liveness:** a TCP check on 8080 only. If liveness depended on the DB, a DB outage would restart every WordPress pod: a restart storm that adds to the failure.
- **Resources:** requests 100m / 192Mi; limits 1 CPU / 512Mi.

### Service `wordpress`
ClusterIP on port 80, forwarding to the container's `http` port (8080). Two things use it:
- the Ingress, for the storefront
- woo-mcp (Phase 2), for the REST API at `http://wordpress.store.svc.cluster.local`

### Ingress `storefront`
`ingressClassName: traefik`, host `shop.localtest.me` → Service `wordpress:80`. When `global.tls.enabled` is true (prod), it also gets a `tls:` block and a cert-manager annotation.

### Secret `wordpress-admin`
The generated admin password, using the same `lookup` pattern. Read it with `make admin-password` (user: `admin`).

### Secret `woocommerce-api-key` (in `store` **and** `mcp`)
The WooCommerce REST credentials: `ck_` and `cs_` each followed by 40 hex characters, the same format WooCommerce generates.

- **Generated once.** `lookup` reads the store copy, and the same values are rendered into both namespaces.
- **Why two copies:** a pod can only mount Secrets from its own namespace. The setup Job (`store`) registers the key; woo-mcp (`mcp`) uses it.
- No RBAC is involved: nothing reads Secrets through the Kubernetes API.

### ConfigMap `store-setup` + Job `store-setup`
The ConfigMap holds `setup.sh`. The Job runs it with wp-cli, using the same image and volume as WordPress.

**How the hook works:**
- The Job is a **Helm hook** (`post-install,post-upgrade`). It runs after every install and every upgrade, once the other resources are ready.
- `hook-delete-policy: before-hook-creation` deletes the previous run's Job just before creating the new one. The last run's logs stay inspectable until the next upgrade.
- **No probes, by design.** A run-to-completion Job is bounded by `activeDeadlineSeconds: 600` and `backoffLimit: 3`. Each wp-cli call also has a 120 s timeout, and calls over 10 s are logged by name.

**Every step is idempotent:**

1. Wait for `wp-config.php` (written by the WordPress pod) and for MariaDB.
2. `wp core is-installed || wp core install …`
3. Install WooCommerce from the baked zip **only if the installed version differs**, activate it, then run `wp wc update` for DB migrations.
4. Set timezone Asia/Kolkata, currency INR, an India store address and pretty permalinks. Skip onboarding, and turn off "coming soon" mode, which would hide the storefront from visitors. Create the shop pages.
5. Enable Cash on Delivery through WooCommerce's own settings API (`wp wc payment_gateway update cod`).
6. Seed 5 products, keyed by SKU, so re-runs never duplicate.
7. Register the REST key:
   - It belongs to a dedicated **`woo-mcp` user with the `shop_manager` role.** That's least privilege: it can manage products and orders, but not plugins or users.
   - The row is written exactly as `WC_Auth::create_keys` writes it: `consumer_key = hmac_sha256(ck, 'wc-api')`, the secret, and `truncated_key` = the last 7 characters.
   - Delete-then-insert by description keeps it idempotent.

## How woo-mcp will authenticate (proven in Phase 1)

In-cluster traffic is plain HTTP, and WooCommerce only accepts Basic auth or query-string keys over HTTPS. Over HTTP it requires **OAuth 1.0a one-legged signatures**.

`scripts/wc-rest-smoke.mjs` implements the signature exactly as `WC_REST_Authentication::check_oauth_signature` verifies it:
- HMAC-SHA256, with key = `consumer_secret + "&"`
- base string = `METHOD & enc(home URL) & enc(sorted, RFC 3986-encoded params)`
- the params are **all query parameters, including `rest_route`**, plus the `oauth_*` fields

**The non-obvious part:** WooCommerce builds the base URL from `get_home_url()`, the *public* `http://shop.localtest.me`, not the internal Service hostname the request was actually sent to.

**Result,** from a pod in the `mcp` namespace: the signed `GET ?rest_route=/wc/v3/products` returns **200** with the seeded products, and the unsigned request returns **401**.

## Verified behaviour

| Check | Result |
|-------|--------|
| `make up` | completes (cluster, image build, k3d import, `helm upgrade --install` with `values-local.yaml`) |
| Storefront | `http://shop.localtest.me/shop/` returns 200 and lists 5 INR products |
| COD | enabled |
| Idempotency | two `helm upgrade`s leave Secrets (hashed), product count, user count, API key rows and settings identical; exactly one setup Job remains (`scripts/check-store-idempotency.sh`) |
| Helm 4 | `lookup` keeps Secrets stable; hooks and `before-hook-creation` work; `helm history` and `helm rollback` work, and the storefront stays up through a rollback |
| Helm 4 difference | vendored subcharts **must** be listed under `dependencies:` in `Chart.yaml`, or `helm lint` fails |

## Known issues (tracked, not DoD-blocking)

- **WP-cron never fires.** WordPress triggers cron with a loopback request to its own URL. Inside the pod, `shop.localtest.me` resolves to 127.0.0.1:80, where nothing listens (Apache is on 8080). Due events (Action Scheduler, cleanups) pile up. Planned fix: `DISABLE_WP_CRON` plus a Kubernetes CronJob running `wp cron event run --due-now`.
- **No mail server.** WooCommerce order emails fail quietly (`sendmail: not found`). This doesn't affect checkout or the DoD.
- **Docker has about 3.9 GB of RAM.** It's enough for the store, but tight once Postgres, the gateway, three MCP servers and the dashboard are added. Raise the Docker Desktop / WSL memory limit to 6–8 GB if pods get OOM-killed.
