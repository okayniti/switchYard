# Production-like deployment on a VPS (k3s)

> **Status: documented, not deployed.** These are the exact steps for running the same chart
> on a single VPS with k3s. They follow from what was verified locally on k3d (which *is* k3s),
> but no VPS was provisioned for this submission. Treat the commands as a runbook to execute,
> not as a record of a deployment.

## Why this works with values only

k3d runs k3s, so a k3s VPS has the same Traefik ingress controller, the same `local-path`
storage class and the same NetworkPolicy enforcement (kube-router). The chart
(`charts/switchyard`) is identical; only `values-prod.yaml` differs from `values-local.yaml`:

| Concern | Local (`values-local.yaml`) | VPS (`values-prod.yaml`) |
|---------|-----------------------------|--------------------------|
| Hosts | `shop/yard/mcp.localtest.me` | `shop/yard/mcp.<domain>`, or `shop.<ip>.sslip.io` etc. with no domain |
| TLS | off | `global.tls.enabled: true`, `clusterIssuer: letsencrypt-prod`: Ingresses get a `tls:` block and a cert-manager annotation |
| Storage class | `local-path` | `local-path` (k3s); set a CSI class on a managed cluster |
| Store secrets | generated by Helm (`lookup`) | `existingSecret` (`mariadb`, `wordpress-admin`, `woocommerce-api-key`), created below |
| Namespaces | created by the chart | `global.createNamespaces: false`: created below, before the Secrets |
| Gateway / Postgres / shipping secrets | generated by Helm | generated by Helm, in-cluster |
| Images | `switchyard-*:dev` via `k3d image import` | `ghcr.io/okayniti/switchyard-*:<git-sha>` |
| Resources | trimmed for an 8 GB laptop | chart defaults, slightly larger |

## 0. Requirements

- **VPS:** Ubuntu 24.04, **≥ 4 GB RAM** (2 vCPU), 20 GB disk. Inbound **80** and **443**
  open (HTTP-01 challenges need 80).
- **DNS:** A records for `shop.<domain>`, `yard.<domain>` and `mcp.<domain>` pointing at the
  VPS IP. With no domain, use `shop.<ip>.sslip.io` (and `yard.`, `mcp.`); they resolve to the
  IP automatically.
- **On your workstation:** Docker with buildx, and push access to `ghcr.io/okayniti`.

## 1. Build and push the images (workstation)

```bash
SHA=$(git rev-parse --short HEAD)
echo "$GHCR_TOKEN" | docker login ghcr.io -u okayniti --password-stdin
# --platform linux/arm64 too if the VPS is ARM (e.g. Oracle Ampere)
docker buildx build --platform linux/amd64 -t ghcr.io/okayniti/switchyard-wordpress:$SHA      --push images/wordpress
docker buildx build --platform linux/amd64 -t ghcr.io/okayniti/switchyard-everything-mcp:$SHA --push images/everything-mcp
for a in woo-mcp shipping-mcp gateway; do
  docker buildx build --platform linux/amd64 -t ghcr.io/okayniti/switchyard-$a:$SHA -f apps/$a/Dockerfile --push .
done
```

The chart has **no `imagePullSecrets`**, so make the five ghcr packages **public** (GitHub →
Packages → Settings → visibility). Otherwise, add an `imagePullSecrets` field to the templates
first.

## 2. Install k3s (VPS)

```bash
# Same k3s as the local k3d cluster (parity). Traefik, local-path and NetworkPolicy are built in.
curl -sfL https://get.k3s.io | INSTALL_K3S_VERSION=v1.35.5+k3s1 sh -
sudo chmod 644 /etc/rancher/k3s/k3s.yaml
export KUBECONFIG=/etc/rancher/k3s/k3s.yaml
kubectl get nodes        # Ready

# Helm 4 (same as local)
curl -fsSL https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-4 | bash
```

## 3. TLS: cert-manager and a Let's Encrypt issuer

```bash
helm repo add jetstack https://charts.jetstack.io && helm repo update
helm install cert-manager jetstack/cert-manager --version v1.21.3 \
  -n cert-manager --create-namespace --set crds.enabled=true --wait

kubectl apply -f - <<'EOF'
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: you@example.com            # expiry notices
    privateKeySecretRef:
      name: letsencrypt-prod
    solvers:
      - http01:
          ingress:
            ingressClassName: traefik
EOF
```

## 4. Namespaces and the existing Secrets

`values-prod.yaml` references these by name, so create them first with random values. They
never touch git, and they survive `helm uninstall` and reinstall.

```bash
for ns in store mcp platform; do kubectl create namespace "$ns"; done

kubectl -n store create secret generic mariadb \
  --from-literal=mariadb-root-password="$(openssl rand -hex 24)" \
  --from-literal=mariadb-password="$(openssl rand -hex 24)"

kubectl -n store create secret generic wordpress-admin \
  --from-literal=admin-password="$(openssl rand -hex 12)"

# WooCommerce REST key: the same values in store (setup Job registers it) and mcp (woo-mcp uses it)
CK="ck_$(openssl rand -hex 20)"; CS="cs_$(openssl rand -hex 20)"
for ns in store mcp; do
  kubectl -n "$ns" create secret generic woocommerce-api-key \
    --from-literal=consumer-key="$CK" --from-literal=consumer-secret="$CS"  # gitleaks:allow (shell variable, not a secret)
done
unset CK CS
```

Postgres, the gateway's keys (`GATEWAY_ENC_KEY`, admin/member passwords) and the shipping
token are generated by Helm in-cluster on first install, exactly as locally.

## 5. Configure and install

Copy the repo (or just `charts/`) to the VPS and fill in the `<placeholders>` in
`charts/switchyard/values-prod.yaml`:

- `global.hosts.*`: your three hostnames
- every `image.tag: <git-sha>`: the `$SHA` from step 1
- `setup.adminEmail`, `gateway.adminEmail`

```bash
helm upgrade --install switchyard charts/switchyard \
  -f charts/switchyard/values-prod.yaml \
  --set-string gateway.llm.apiKey="$LLM_API_KEY" \
  --wait --wait-for-jobs --timeout 15m
```

## 6. Verify

```bash
kubectl get pods -A                       # all Running/Ready; store-setup Completed
kubectl get certificate -A                # storefront-tls and gateway-tls READY=True (1–2 min)
curl -sI https://shop.<domain>/shop/      # 200
curl -s -o /dev/null -w '%{http_code}\n' -X POST https://mcp.<domain>/mcp   # 401 without a key

# Logins
kubectl -n store get secret wordpress-admin -o jsonpath='{.data.admin-password}' | base64 -d; echo
kubectl -n platform get secret gateway -o jsonpath='{.data.admin-password}' | base64 -d; echo
```

Then connect an MCP client to `https://mcp.<domain>/mcp` with a key from
`https://yard.<domain>`.

## 7. Upgrade and roll back

```bash
# New release: build/push images with a new $SHA (step 1), then
helm upgrade switchyard charts/switchyard -f charts/switchyard/values-prod.yaml \
  --set wordpress.image.tag=$SHA --set gateway.image.tag=$SHA \
  --set wooMcp.image.tag=$SHA --set shippingMcp.image.tag=$SHA --set everythingMcp.image.tag=$SHA \
  --wait --wait-for-jobs
helm history switchyard
helm rollback switchyard <revision> --wait
```

- PVCs (MariaDB, WordPress content, Postgres) and the Secrets are untouched by upgrade and
  rollback.
- The store setup Job is idempotent and re-runs on every upgrade.
- Before upgrading WooCommerce (a new WordPress image), dump the DB:

  ```bash
  kubectl -n store exec mariadb-0 -- sh -c \
    'mariadb-dump -uroot -p"$MARIADB_ROOT_PASSWORD" wordpress' > wordpress-$(date +%F).sql
  ```

## Differences from local worth knowing

- **Single node.** `local-path` volumes and the `ReadWriteOnce` WordPress volume assume one
  node. Multi-node needs a CSI storage class (and RWX, or no shared volume, for WordPress).
- **No default-deny egress yet.** Only woo-mcp has an ingress NetworkPolicy. On a public VPS,
  adding per-namespace default-deny is the first hardening step.
- **Back up Secret `platform/gateway`.** Its `enc-key` decrypts the upstream credentials
  stored in Postgres; losing it means re-entering those credentials.
