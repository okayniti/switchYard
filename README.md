# Switchyard

WooCommerce hosting with a **Team MCP Gateway** on Kubernetes. One WooCommerce store, our own
WooCommerce MCP server, two more upstream MCP servers, and a gateway + dashboard that exposes
every enabled server's tools through **one** `/mcp` endpoint and a chat agent. Everything runs
in-cluster and installs with **one Helm chart**; local (k3d) and production-like (k3s) differ
only by values files.

| URL (local) | What |
|-------------|------|
| http://shop.localtest.me | storefront (WordPress + WooCommerce) |
| http://shop.localtest.me/wp-admin/ | WooCommerce admin |
| http://yard.localtest.me | dashboard (servers, members, API keys, audit log, chat) |
| http://mcp.localtest.me/mcp | the gateway's MCP endpoint (Streamable HTTP, `Authorization: Bearer <key>`) |

Docs: [design](docs/DESIGN.md) · [threat model](docs/THREAT_MODEL.md) ·
[env contract](docs/ENV.md) · [requirements matrix](docs/REQUIREMENTS_MATRIX.md) ·
[assignment](docs/ASSIGNMENT.md)

## Local setup

```bash
git clone https://github.com/okayniti/switchYard && cd switchYard
git config core.hooksPath .githooks        # enables the gitleaks pre-commit secret scan

make up                                    # cluster + images + helm install (≈5 min first time)
make up LLM_API_KEY=gsk_...                # same, and stores the LLM key for chat
make llm-key LLM_API_KEY=gsk_...           # ONLY set/replace the LLM key + restart the gateway (no rebuild)
```

`make up` is idempotent; run it again after any change. Under the hood it:

1. **`make cluster`**: `scripts/k3d-up.sh` creates k3d cluster `switchyard` (1 server,
   host `80/443` → Traefik, API on `127.0.0.1:6550`). Skipped if it exists.
2. **`make images`**: builds `switchyard-wordpress`, `switchyard-everything-mcp` and every
   `apps/<name>/Dockerfile` (`woo-mcp`, `shipping-mcp`, `gateway`) as `:dev`.
3. **`make import`**: `k3d image import`, so nothing is pulled from a registry.
4. **`make install`**: `helm upgrade --install switchyard charts/switchyard -f
   charts/switchyard/values-local.yaml --wait --wait-for-jobs`. An app whose image doesn't
   exist yet is installed with `<app>.enabled=false`.

(On Windows, run these from Git Bash.)

The LLM key is passed as `--set-string gateway.llm.apiKey=…` into the `llm` Secret. It's never
echoed, never written to a values file, and kept across later `make up` runs that omit it.
`make llm-key` changes only that Secret and restarts the gateway. The provider and model are
plain values (`gateway.llm.baseUrl`, `gateway.llm.model`, default Groq +
`openai/gpt-oss-120b`). Change them with `helm upgrade … --set gateway.llm.model=<model>` or in
`values.yaml`; no image rebuild is needed.

**Demo reset:** `bash scripts/demo-reset.sh [LLM_API_KEY=…]` starts the cluster if stopped,
re-runs `make up`, waits until every pod is Ready, smoke-tests the URLs and **prints every URL
and login**. `--wipe` deletes the cluster and all data first (asks for confirmation).

**Logins:** every password is generated by Helm into a Kubernetes Secret on first install.
None is in git.

```bash
make admin-password            # WooCommerce admin (user: admin)
make gateway-admin-password    # dashboard: admin@switchyard.local (A) and member@switchyard.local (B)
```

Other targets: `make status` (pods, PVCs, Services, Ingress, NetworkPolicies per namespace),
`make down` (deletes the cluster **and all data**).

### Local domains: `*.localtest.me`

`localtest.me` is a public DNS zone where every name resolves to `127.0.0.1`, so
`shop.localtest.me` → your machine → k3d's load balancer (host port 80) → Traefik → the Ingress
whose `host` matches. No hosts-file edits and no port numbers.

**Fallback** (offline, or a DNS resolver that blocks rebinding to 127.0.0.1): add the three
hosts to `/etc/hosts` (Windows: `C:\Windows\System32\drivers\etc\hosts`, as Administrator):

```
127.0.0.1  shop.localtest.me yard.localtest.me mcp.localtest.me
```

### Resource sizing: an 8 GB laptop vs production

The local stack is sized to fit a laptop with **8 GB RAM total**, where WSL/Docker gets
about 4–5 GB. Only `values-local.yaml` is shrunk; `values-prod.yaml` keeps the chart's larger
defaults. Every workload still has requests **and** limits, and each limit is the smallest
that was observed to run.

| Workload | `values-local.yaml` request → limit | Tuning | `values-prod.yaml` |
|----------|-------------------------------------|--------|--------------------|
| woo-mcp, shipping-mcp, everything-mcp, gateway | 64Mi → 256Mi | | chart defaults (64–256Mi → 192–768Mi) |
| WordPress | 128Mi → 256Mi | Apache prefork capped at **4 workers** (each is a ~30–60 MB PHP process; the default 150 would blow the limit under load) | 256Mi → 768Mi, 10 workers |
| MariaDB | 128Mi → 256Mi | `--innodb-buffer-pool-size=64M` (default 128M), `--performance-schema=OFF` (~100 MB saved), `--max-connections=30` | 384Mi → 768Mi, defaults |
| Postgres | 64Mi → 256Mi | `shared_buffers=32MB`, `max_connections=20`, `work_mem=2MB` | 128Mi → 384Mi, defaults |
| store setup Job | 128Mi → **384Mi** | see below | 128Mi → 512Mi |
| k3s itself | | `metrics-server` disabled (no HPA uses it) | k3s defaults |

**Why the setup Job gets 384Mi, more than everything else.** At 256Mi it was
**OOM-killed** (exit 137, four retries) while running `wp rewrite structure`. wp-cli boots all of
WordPress plus WooCommerce in a single PHP process, and flushing rewrite rules peaks above
256 MB. The Job is short-lived and runs alone after install/upgrade, so the higher limit
costs nothing at steady state, while the long-running pods stay at 256Mi.

Measured with the full stack running (7 pods, `docker stats --no-stream`): the k3d node
uses **≈1.6 GiB**, leaving ~1.6 GB free in a 3.7 GB Docker VM.

Builds are memory-heavy too, so `make images` builds **one image at a time**, `make import`
imports them one at a time, and the build cache is pruned afterwards (`docker builder prune
-f`). Stop unrelated containers before `make up` on a small machine.

### Troubleshooting

| Symptom | Fix |
|---------|-----|
| `kubectl` hangs / `EOF` / TLS handshake timeout after Docker restarted (Windows) | the k3d load balancer kept the server's old IP: `docker restart k3d-switchyard-serverlb` (`demo-reset.sh` does this automatically) |
| kubeconfig points at `host.docker.internal` and times out (Windows) | clusters created by `scripts/k3d-up.sh` bind the API to `127.0.0.1:6550`; for an older cluster run `kubectl config set-cluster k3d-switchyard --server=https://127.0.0.1:<port>` |
| `http://shop.localtest.me` doesn't resolve | use the hosts-file fallback above |
| Browser shows **`ERR_CONNECTION_RESET`** (or `curl` gets `000`/connection reset) on `*.localtest.me` | the k3d load balancer is forwarding port 80 to a stale node IP after Docker restarted (its log shows `connect() failed (111)`): `docker restart k3d-switchyard-serverlb`, or `bash scripts/demo-reset.sh`. If only one host fails, its pod is restarting: `make status` |
| `kubectl` / `docker` hang, TLS handshake timeouts, k3s at very high CPU | the Docker VM is out of memory (8 GB laptop): stop unrelated containers (`docker ps`, `docker stop …`). The local values are sized for a ~4 GB VM; see [sizing](#resource-sizing-an-8-gb-laptop-vs-production) |
| pods `OOMKilled` / `Pending` | same: free memory or raise the WSL2 cap (`%UserProfile%\.wslconfig`: `[wsl2]` `memory=6GB`, then `wsl --shutdown` and restart Docker) |
| setup Job `OOMKilled` (exit 137) | wp-cli needs more than 256Mi; `values-local.yaml` gives the Job 384Mi. Raise `setup.resources.limits.memory` if you add plugins |
| chat says the model doesn't exist / was decommissioned | the provider retired the model (Groq retired `llama-3.3-70b-versatile`). Pick a current one and run `helm upgrade switchyard charts/switchyard -f charts/switchyard/values-local.yaml --set gateway.llm.model=<model> --wait` (or change `gateway.llm.model` in `values.yaml`); no image rebuild needed |
| chat says no LLM key | `make llm-key LLM_API_KEY=…` |
| setup Job failed | `kubectl logs -n store job/store-setup`; every step is idempotent, so `make install` re-runs it safely |

## Place an order (storefront)

1. Open **http://shop.localtest.me/shop/**. Five products are seeded (₹299–₹699); products
   created through the chat or MCP appear here too.
2. **Add to cart** → **View cart** → **Proceed to checkout**.
3. Fill in the billing address (any Indian address works, e.g. Bengaluru, KA, 560001) and choose
   **Cash on delivery**, the only payment method, enabled by the setup Job. Then **Place order**.
4. Confirm it in **WooCommerce admin** → http://shop.localtest.me/wp-admin/ → *WooCommerce →
   Orders* (login from `make admin-password`). The store runs in **Asia/Kolkata** with **INR**,
   so "orders today" means today in IST.

## Connect an external MCP client

Every team member uses **one URL and their own key**. They never see or configure an upstream
server or its credentials.

1. Log in to the dashboard (<http://yard.localtest.me>; logins: `make gateway-admin-password`).
2. **My keys → Generate key.** The key (`syk_…`) is shown **once**, together with a ready-made
   Claude Code command. The gateway stores only its SHA-256.
3. Add the gateway to your client:

   **Claude Code**
   ```bash
   claude mcp add --transport http switchyard http://mcp.localtest.me/mcp \
     --header "Authorization: Bearer syk_..."
   ```

   **Cursor** (`~/.cursor/mcp.json`)
   ```json
   { "mcpServers": { "switchyard": { "url": "http://mcp.localtest.me/mcp",
       "headers": { "Authorization": "Bearer syk_..." } } } }
   ```

   **Any other client:** Streamable HTTP transport, URL `http://mcp.localtest.me/mcp`, header
   `Authorization: Bearer <key>`.

You'll see the tools of every **enabled and reachable** server, named `<server>__<tool>`
(`woo__list_orders`, `shipping__quote_shipping`, `everything__echo`…). The prefix is how two
servers can both have a `search` tool (`woo__search`, `shipping__search`). When an admin disables
a server, or one goes down, connected clients get `tools/list_changed` and its tools disappear.

Try: *"What orders came in today?"*, or *"Look up order 20 and quote express shipping to PIN
560001 for 1 kg"* (uses two servers).

- **Revoked key:** the very next request gets `401`, even inside an open session.
- **Browser-based clients** must run on an origin listed in `MCP_ALLOWED_ORIGINS`; CLI clients
  send no `Origin` and are unaffected.

## Use the chat agent

Dashboard → **Chat**. Ask in plain language, e.g. *"Create a product called Brass Lamp priced at
799"* or *"What orders came in today?"*. Under each answer the dashboard lists every tool the agent
called, with its arguments, result, duration and whether it succeeded.

- The agent calls tools **through the gateway's own `/mcp` as you**: for each message it mints a
  10-minute key for your user and revokes it afterwards. It can do exactly what you can, and its
  calls appear in the **Audit log** under your name with source `chat`.
- At most 8 tool-calling steps per message; each tool result is capped at 4,000 characters.
- The LLM key never reaches the browser.

### The LLM model is a Helm value, and providers retire models

Provider and model are plain chart values: `gateway.llm.baseUrl` (default Groq,
`https://api.groq.com/openai/v1`) and `gateway.llm.model` (default `openai/gpt-oss-120b`). Any
OpenAI-compatible Chat Completions endpoint works, **as long as the model supports tool calling**.

Providers retire models. Groq retired `llama-3.3-70b-versatile`, which this project first used, and
chat then failed with `HTTP 404 model_not_found`. To switch:

```bash
# 1. See which models your key can use (run inside the gateway pod; the key isn't printed)
kubectl exec -n platform deploy/gateway -- node -e 'fetch(process.env.LLM_BASE_URL+"/models",
  {headers:{authorization:"Bearer "+process.env.LLM_API_KEY}}).then(r=>r.json())
  .then(j=>console.log(j.data.map(m=>m.id).sort().join("\n")))'

# 2. Point the gateway at one (no image rebuild; the pod restarts with the new env)
helm upgrade switchyard charts/switchyard -f charts/switchyard/values-local.yaml \
  --set gateway.llm.model=<model> --wait
```

To make it permanent, change `gateway.llm.model` in `values.yaml` (or `values-prod.yaml`).

**Free-tier rate limits:** Groq's free tier allows about 8,000 tokens per minute for
`gpt-oss-120b`, and one chat turn with all 25 tools is about 2,400 tokens. The gateway waits and
retries on HTTP 429 (up to 3 times, 30 s total); beyond that the chat shows the provider's
rate-limit message. Wait a minute, or use a paid tier.

## Production-like deployment (VPS with k3s)

> **Status: documented, not deployed.** No VPS was provisioned for this submission. The full,
> exact runbook is in **[docs/VPS.md](docs/VPS.md)**.

The **same chart** runs on a single VPS with k3s. k3s bundles Traefik, the `local-path`
storage class and NetworkPolicy enforcement, exactly like k3d locally. Only
`charts/switchyard/values-prod.yaml` changes; no template differs.

### What changes, via values only

| Concern | `values-local.yaml` | `values-prod.yaml` |
|---------|---------------------|--------------------|
| Hostnames (`global.hosts`) | `shop/yard/mcp.localtest.me` | `shop/yard/mcp.<your-domain>` (or `*.<ip>.sslip.io` with no domain) |
| TLS (`global.tls`) | off, plain HTTP | `enabled: true` + `clusterIssuer: letsencrypt-prod`: each Ingress gets a `tls:` block and a cert-manager annotation, and certificates are issued automatically |
| Storage (`global.storageClassName`) | `local-path` | `local-path` (k3s default); on a managed cluster, set your CSI class here |
| Store secrets | generated by Helm (`lookup` keeps them stable) | `existingSecret` for MariaDB, WP admin and the WooCommerce key: created out-of-band, so they survive a reinstall and never depend on `lookup` |
| Gateway / Postgres / shipping secrets | generated in-cluster by Helm | same (generated in-cluster, never in git) |
| Images | `switchyard-*:dev`, `k3d image import`, `IfNotPresent` | `ghcr.io/okayniti/switchyard-*:<git-sha>` (build multi-arch with `docker buildx` if the VPS is ARM) |
| Resources | small requests/limits | slightly larger |

### In short (full commands in [docs/VPS.md](docs/VPS.md))

1. Build and push the five images to `ghcr.io/okayniti/switchyard-*:<git-sha>` with
   `docker buildx`, and make the packages public (the chart has no `imagePullSecrets`).
2. On the VPS: install k3s `v1.35.5+k3s1` (the same version as local), then cert-manager
   `v1.21.3` with a `letsencrypt-prod` ClusterIssuer (HTTP-01 through Traefik).
3. Create the `store`, `mcp` and `platform` namespaces and the three `existingSecret`s with
   `openssl rand` (`values-prod.yaml` sets `global.createNamespaces: false` so Helm doesn't try
   to own them).
4. Fill in the `<placeholders>` in `values-prod.yaml` (hosts, image tag, admin email) and run
   `helm upgrade --install switchyard charts/switchyard -f charts/switchyard/values-prod.yaml
   --set-string gateway.llm.apiKey=... --wait --wait-for-jobs`.

## Upgrades and rollback

```bash
helm upgrade switchyard charts/switchyard -f charts/switchyard/values-local.yaml --wait --wait-for-jobs
helm history switchyard                   # every revision with its status
helm rollback switchyard <revision> --wait   # restores the previous revision's manifests
```

**Verified locally on the final chart:**

- Many `helm upgrade` runs; the setup Job re-runs cleanly every time.
- **`helm rollback`**, for real. A bad upgrade (revision 28: `values-prod.yaml` with
  placeholder image tags applied by mistake to the local cluster) put every Deployment on an
  invalid image. The rolling-update Deployments kept their old pods serving; WordPress
  (`Recreate`) went down. `helm rollback switchyard 27 --wait` restored everything in **13 s**:
  all pods Ready, storefront 200, every generated password and Secret unchanged, products and
  orders intact.

What makes this safe:

- **Generated secrets never rotate.** Templates read the existing Secret with `lookup` and
  reuse its values; prod uses `existingSecret`.
- **The store setup Job is idempotent.** It runs as a `post-install,post-upgrade` hook (WP core
  install only if missing; WooCommerce reinstalled only if the version differs, then `wp wc
  update` for DB migrations; products keyed by SKU; the REST key is delete-then-insert).
  `scripts/check-store-idempotency.sh` runs two upgrades and asserts that Secrets, products,
  users, API keys and settings are identical. Its full run wasn't completed on the final
  chart; the individual checks were done by hand. A rollback re-runs nothing destructive.
- **Data lives on PVCs** (MariaDB, WordPress content, Postgres), which upgrades and rollbacks
  don't touch, and the store PVC plus its Secrets carry `helm.sh/resource-policy: keep`, so
  they also survive an uninstall.
- **Upgrading WooCommerce** = bump `WOOCOMMERCE_VERSION` and the checksum in
  `images/wordpress/Dockerfile`, rebuild, `helm upgrade`. The Job installs the new zip and runs
  the DB update. Take a DB dump first (`kubectl exec -n store mariadb-0 -- mariadb-dump …`).
- **Gateway / MCP servers** are stateless Deployments: `--set gateway.image.tag=<sha>` rolls
  them, and `helm rollback` restores the previous tag.

## What's done / what's not

An honest inventory; it matches [docs/THREAT_MODEL.md](docs/THREAT_MODEL.md). "Verified" means
run against the local cluster during development. The end-to-end Definition of Done check
(`scripts/dod.ts`, `make dod`) is owned by the gateway session.

### Built

**Platform and Kubernetes (verified)**

- **One Helm chart**, `values-local.yaml` and `values-prod.yaml`, and three namespaces
  (`store`, `mcp`, `platform`).
- Every workload has readiness and liveness probes plus requests/limits, and runs non-root
  with a read-only root filesystem and all capabilities dropped. Jobs use deadlines instead of
  probes.
- PVCs for MariaDB, WordPress content and Postgres.
- Ingress with stable URLs (`*.localtest.me`, with a hosts-file fallback).
- Every secret is generated by Helm into Kubernetes Secrets (stable via `lookup`) or comes from
  `existingSecret` in prod. None is in git; a gitleaks pre-commit hook scans every commit.
- A **NetworkPolicy** lets only gateway pods reach woo-mcp. Verified: allowed from the gateway,
  refused from `store`.
- `helm upgrade`, `helm history` and a real `helm rollback`.

**Store (verified)**

- WordPress 7.1.3 and WooCommerce 11.2.1, baked into a pinned image.
- An idempotent setup Job: core install, WooCommerce, Asia/Kolkata, INR, **Cash on Delivery**,
  seeded products, and a REST key for a `shop_manager` user.
- A COD checkout creates an order.
- WordPress outbound HTTP is blocked.

**MCP servers**

- **woo-mcp** (ours): Streamable HTTP; `list_products`, `create_product`, `list_orders`
  (`today` in IST), `get_order`, `update_order_status`, `search`. Talks to the store over the
  WooCommerce REST API with OAuth 1.0a signing over in-cluster HTTP. Verified `tools/list` and
  `list_products` in-cluster.
- **shipping-mcp** (ours, requires a bearer token).
- **everything-mcp** (the official reference server, pinned).

**Gateway and dashboard** (built by the gateway session; details in DESIGN and THREAT_MODEL)

- One `/mcp` endpoint with `<server>__<tool>` naming for collisions.
- `tools/list` is served from a cache; `tools/call` is routed with a 15 s timeout and clear
  errors.
- A health loop shows Connected / Unreachable (with a reason) / Disabled, and sends
  `tools/list_changed` when the tool set changes.
- Admin and member roles. API keys are SHA-256 hashed and checked on every request; keys can
  be revoked, and admins can issue and revoke keys for members.
- Upstream credentials are AES-256-GCM encrypted and write-only.
- An audit row for every tool call through `executeToolCall`.
- A chat agent that acts as the logged-in user.
- Origin validation on `/mcp`, and a minimal SSRF guard on upstream URLs.

### Not built / known gaps

| Gap | Note |
|-----|------|
| Per-role / per-tool permissions | any member can call every tool, including writes; the audit log shows who (THREAT_MODEL §1) |
| Per-key rate limits | one member can use up the shared LLM quota |
| Tool-definition pinning (rug-pull detection) | changed descriptions are served on the next health check (§3) |
| Confirmation step for write tools in chat | |
| Audit of admin actions | only tool calls are audited |
| Email/link-based invites | "invite" = the admin creates the member's account with an initial password |
| `Host` header validation on `/mcp` | Origin is validated |
| Default-deny NetworkPolicies | only woo-mcp has a policy; the other MCP servers rely on ClusterIP (and the shipping token) |
| VPS deployment | **documented, not deployed** ([docs/VPS.md](docs/VPS.md)) |
| Multi-store bonus, OAuth on the gateway, many-tools handling, hosted MCP servers, multi-replica gateway, `/metrics` | not attempted |

### Stand-out items attempted

- **Security hardening (partial):** SSRF guard on upstream URLs; non-root, read-only,
  no-capability containers everywhere; a NetworkPolicy isolating woo-mcp; upstream credentials
  encrypted at rest; no Kubernetes API access for any pod. Not done: default-deny everywhere.
- **Upgrades and rollback:** documented and exercised locally (an idempotent setup hook, stable
  secrets, a real rollback). See [Upgrades and rollback](#upgrades-and-rollback).
- **Production-like VPS:** the values and the runbook only; not deployed.
